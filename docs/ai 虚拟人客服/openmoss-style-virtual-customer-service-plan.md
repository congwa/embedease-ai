# EmbedeaseAI 虚拟人客服公司化运营方案

本文是 `embedease-ai` 在“AI 虚拟人客服”方向上的总计划文档。它的业务职责不是描述单个 Agent 怎么写，而是回答系统为什么要从“单对话客服”升级成“像公司一样运转的多角色客服组织”，以及这套组织如何分阶段落地到你当前项目中。

## 1. 目标重述

你要做的不是“多配几个客服 prompt”，而是把客服系统重构成一个可持续运营的 AI 组织：

- 有前台接待和问题分类能力
- 有按问题域分工的处理角色
- 有审查、返工、升级、巡检机制
- 有周期性任务和运营复盘能力
- 有后台管理、绩效统计和规则配置能力

对应到 OpenMOSS 的表达，可以转译成 `embedease-ai` 里的业务目标：

- 像公司一样运转：不是单 Agent 回答，而是多角色协同处理客户问题
- 全自动运行：会话内实时调度，离线任务由调度器自动触发
- 闭环质量控制：回复前后都有审查标准，低质量结果必须返工
- 永不停摆：异常会话、卡住工单、失败任务都能被巡查 Agent 发现并修复
- 绩效驱动：不同 Agent 的通过率、转人工率、返工率可量化
- Skill 可插拔：能力来自 Skill 绑定，不把业务知识全写死在代码里
- 7x24 循环运营：支持每日巡检、知识复盘、工单追踪、客户回访
- 内置管理后台：运营能看状态、改规则、调 Agent、审结果

## 2. 为什么你的客服改造应该走这条路

传统单客服 Agent 的主要问题不是“不会说”，而是“不会组织”：

- 一个 Agent 同时做接待、判断、处理、安抚、升级，职责混乱
- 复杂问题只能靠上下文硬扛，轮次一长就容易跑偏
- 缺少显式审查机制，错误回答只能靠用户发现
- 缺少系统巡检，任务一旦中断就停在半路
- 缺少绩效和质量统计，无法知道哪个 Agent 真有效

你的项目已经有一些可复用资产：

- 已有 `Supervisor + SubAgent + Handoff` 骨架
- 已有 Agent 配置、Skill 管理、客服工作台
- 已有 LangGraph Agent 运行基础
- 已有后台配置入口和 SSE 事件流

因此最合理的路线不是照搬 OpenMOSS 的实现细节，而是借鉴它的“组织模型”，把你现有系统升级成一套面向客服运营的多角色运行框架。

## 3. 核心设计原则

### 3.1 先按业务角色拆，不按技术能力拆

角色应该按客服业务职责定义，而不是按“检索 Agent”“工具 Agent”“总结 Agent”这种技术名字定义。

### 3.2 先做单主线闭环，再做复杂并行

客服场景首先强调口径统一、状态清晰、升级可靠。第一阶段不要追求大规模并行协作，先确保“接待 -> 处理 -> 审查 -> 交付/升级”的主链路跑通。

### 3.3 Skill 决定能力边界，Flow 决定协作顺序

Agent 只代表岗位。真正的能力边界来自 Skill 绑定，真正的流转逻辑来自流程定义。

### 3.4 质量和可恢复性必须是运行时能力

审查、返工、超时、卡死恢复、转人工，都不能只写在 prompt 里，必须有代码层状态机和调度规则兜底。

## 4. 目标组织模型

建议把虚拟人客服组织拆成四层角色。

### 4.1 L0 入口层

- `front_desk_agent`
  - 业务职责：接待客户、识别意图、判断情绪、初始化问题单
  - 适用场景：所有新会话入口
  - 输出：问题标签、紧急度、是否需立即转人工

### 4.2 L1 编排层

- `service_planner_agent`
  - 业务职责：像总监一样拆解处理路径，决定当前应该由哪个岗位接手
  - 适用场景：会话首轮、状态变化、返工后重分派、复杂问题升级
  - 输出：当前处理节点、责任 Agent、完成标准、升级条件

这个角色就是你现在项目里最接近 OpenMOSS “规划者”的部分，建议在第一阶段由现有 Supervisor 演进而来。

### 4.3 L2 执行层

第一批建议保留 5 个问题域执行 Agent：

- `emotion_deescalation_agent`
  - 业务职责：接住情绪、降低对抗、把会话拉回可处理状态
- `faq_policy_agent`
  - 业务职责：解释规则、政策、流程、时效，控制承诺边界
- `case_intake_agent`
  - 业务职责：补齐订单、渠道、故障现象、凭证等关键信息
- `resolution_execution_agent`
  - 业务职责：依据 SOP 推进处理，给出明确下一步与时效
- `handoff_orchestrator_agent`
  - 业务职责：生成转人工摘要、触发升级、保障人工顺利接管

第二阶段再按需要细分专科执行 Agent：

- `refund_policy_agent`
- `logistics_delay_agent`
- `quality_issue_agent`
- `billing_dispute_agent`
- `vip_retention_agent`

### 4.4 L3 保障层

- `quality_reviewer_agent`
  - 业务职责：审查执行结果是否符合业务规则、语气规范、风险边界
  - 类比 OpenMOSS 的审查者
- `operations_patrol_agent`
  - 业务职责：巡检卡住会话、失败任务、长时间未推进工单、异常返工循环
  - 类比 OpenMOSS 的巡查者
- `knowledge_curator_agent`
  - 业务职责：分析高频问题、发现知识缺口、生成 FAQ/SOP 待补充项
  - 适用场景：日常运营复盘，不直接参与单轮对话

## 5. 客服任务模型

为了让系统像公司一样运转，不能只管理“消息”，还要管理“任务”。

建议把客服任务分成两类：

### 5.1 会话内实时任务

由客户消息触发，要求低延迟处理：

- 新问题接待
- 标签重判
- 信息补齐
- 规则解释
- 方案推进
- 转人工
- 回复审查

### 5.2 会话外运营任务

由调度器或 recurring 规则触发：

- 超时未处理会话巡检
- 高风险客诉回访
- 每日转人工原因复盘
- 每日知识缺口总结
- 每日 Agent 绩效统计
- 每周 SOP/FAQ 质量审计

这部分就是你未来接 OpenMOSS “cron 自主唤醒”的最佳切入点，但在 `embedease-ai` 里建议先实现为独立后台调度器，而不是把所有任务都塞进聊天主链路。

## 6. 闭环处理流程

建议把标准客服闭环固定成以下状态链路：

```text
new
-> triaged
-> in_progress
-> pending_review
-> resolved
-> handoff_pending
-> handed_off
-> closed
```

同时允许以下异常路径：

```text
pending_review -> rework_required -> in_progress
in_progress -> blocked
blocked -> patrol_recovered -> in_progress
任意状态 -> handoff_pending
```

### 6.1 主处理链

1. `front_desk_agent` 创建问题单，写入标签、情绪、优先级
2. `service_planner_agent` 选择当前责任执行 Agent
3. 执行 Agent 完成当前节点任务
4. `quality_reviewer_agent` 审查输出
5. 通过则回复用户并推进状态，不通过则驳回返工
6. 达到升级条件时交给 `handoff_orchestrator_agent`

### 6.2 返工机制

返工不应该只是“再来一次”，而要带原因：

- 审查不通过原因
- 缺失的业务字段
- 违规承诺点
- 语气风险点
- 需要补充的证据

返工后的执行 Agent 必须收到结构化反馈，而不是只收到一句“请重试”。

## 7. 质量控制设计

### 7.1 审查维度

`quality_reviewer_agent` 至少检查以下五项：

- 事实正确性：是否引用了正确政策、流程、时效
- 业务合规性：是否越权承诺、是否触发敏感边界
- 信息完整性：是否缺少继续推进所需关键信息
- 沟通质量：是否有安抚、是否清晰、是否可执行
- 升级合理性：该转人工时是否真的升级

### 7.2 审查结果结构

建议输出结构化对象：

```json
{
  "passed": false,
  "score": 72,
  "risk_level": "medium",
  "rework_required": true,
  "reasons": [
    "缺少订单号，无法进入处理推进",
    "回复中承诺了未确认的赔付结果"
  ],
  "suggested_next_agent": "case_intake_agent"
}
```

### 7.3 审查规则

- 高风险违规直接驳回，不允许直接对外回复
- 中风险问题允许一次返工
- 连续两次返工失败，自动升级人工或升级到更高阶 Agent

## 8. 巡查与自愈设计

`operations_patrol_agent` 不参与日常对话，而是后台巡检角色。

它要解决四类问题：

- 会话卡住：长时间没有节点推进
- Agent 失败：执行超时、模型失败、工具失败
- 返工死循环：同一问题在多个 Agent 间来回跳转
- 异常高风险：负面情绪持续升高但没有人工介入

建议定义自动巡查动作：

- 标记 `blocked`
- 记录 `block_reason`
- 自动重试一次
- 触发备用 Agent 或降级路径
- 触发转人工
- 给后台发送告警事件

## 9. 绩效体系设计

绩效不是为了游戏化，而是为了运营知道哪一类 Agent 值得继续扩容、哪一类策略需要修。

建议按 Agent、Skill、流程版本三个维度统计：

- 首次通过率
- 平均返工次数
- 转人工率
- 平均处理时长
- 用户负面情绪下降率
- 知识命中率
- 违规驳回率

建议把 `quality_reviewer_agent` 的结果直接映射为积分：

- 审查通过 + 分
- 高分通过额外加分
- 驳回扣分
- 高风险违规重扣分
- 巡查恢复成功计入运维绩效

后台可以提供：

- Agent 排行榜
- Flow 版本对比
- Skill 效果对比
- Top 驳回原因

## 10. Skill 可插拔体系

你当前项目很适合把 Skill 升级成岗位能力合同。

建议统一成五类 Skill：

- `persona_skill`
  - 定义语气、人设、安抚风格、禁忌表达
- `policy_skill`
  - 定义赔付边界、升级条件、禁止承诺项
- `workflow_skill`
  - 定义处理步骤和输出格式要求
- `tool_skill`
  - 定义可调用工具及参数边界
- `knowledge_skill`
  - 定义可见 FAQ、SOP、政策和案例知识范围

AgentTemplate 的业务含义应变成：

```text
岗位定义
+ 技能绑定
+ 工具范围
+ 审查标准
+ 升级规则
```

这样后续你做“虚拟人客服”时，可以把不同品牌、不同业务线、不同渠道的客服人格和规则做成组合配置，而不是复制 Agent 代码。

## 11. 运行时架构建议

结合你当前项目，不建议一步跳到最重形态。建议按三层建设。

### 11.1 第一层：会话编排层

复用当前 LangGraph Agent 运行时，先把现有 Supervisor 升级成：

- 问题单创建器
- 节点编排器
- 执行 Agent 分派器
- 审查结果处理器

### 11.2 第二层：任务调度层

新增独立调度器，负责：

- recurring 任务
- 巡查任务
- 绩效计算任务
- 知识复盘任务

可以先用简单 cron / APScheduler / Celery Beat 级别方案，不必一开始追求复杂分布式调度。

### 11.3 第三层：运营管理层

管理后台至少包含：

- 会话列表与问题状态
- 当前流程节点与责任 Agent
- 转人工队列
- 审查记录
- 巡查告警
- Agent 绩效榜
- Skill 管理
- Prompt/Flow 版本管理

## 12. 与当前 `embedease-ai` 的映射关系

### 12.1 可以直接复用的部分

- `backend/app/services/agent/core/*`
  - 作为运行时构建骨架继续保留
- `backend/app/services/support/handoff.py`
  - 作为人工升级能力继续保留
- `backend/app/routers/support.py`
  - 继续承载客服工作台与人工接管接口
- `system_config` 和现有 Agent 配置体系
  - 作为第一阶段的配置入口继续使用

### 12.2 必须新增的部分

- `task` / `job` 概念，而不是只靠 message 流转
- 审查 Agent 与审查结果存储
- 巡查 Agent 与异常恢复记录
- 绩效统计模型
- recurring 任务定义与执行器
- 流程定义 `FlowDefinition / FlowVersion / FlowNode / FlowEdge`

### 12.3 第一阶段不要做的部分

- 不要一开始就做大量并行子 Agent
- 不要先做过度复杂的可视化拖拽编排器
- 不要先做通用企业级组织引擎
- 不要先做完全自动化的全场景自主运营

第一阶段最重要的是把“实时客服闭环”跑通。

## 13. 建议的数据模型补充

建议在现有会话模型外新增以下核心实体：

- `service_ticket`
  - 对应一条客户问题单
- `service_task`
  - 对应一次待执行工作项
- `service_review`
  - 对应一次审查记录
- `service_patrol_event`
  - 对应一次巡查发现与处理动作
- `agent_score_snapshot`
  - 对应某时间窗口的绩效快照
- `flow_definition`
  - 对应业务流程定义
- `flow_version`
  - 对应流程版本

会话态建议至少新增这些字段：

- `primary_issue_tag`
- `current_agent_tag`
- `complaint_status`
- `priority_level`
- `unresolved_turns`
- `review_status`
- `review_score`
- `handoff_required`
- `handoff_reason`
- `block_reason`
- `last_patrol_at`

## 14. 后台管理能力规划

建议后台按四个视角拆页面：

### 14.1 运营视角

- 问题单列表
- 当前状态分布
- 转人工队列
- 高风险会话

### 14.2 质控视角

- 审查记录
- 驳回原因排行
- Flow/Agent 质量对比
- 高风险承诺告警

### 14.3 运维视角

- 巡查事件
- 阻塞会话
- 自动恢复结果
- Agent 失败率

### 14.4 配置视角

- AgentTemplate 管理
- Skill 绑定管理
- FlowDefinition 管理
- Prompt / Policy 版本管理

## 15. 分阶段实施路线

### Phase 1：客服主链路重构

目标：把“单聊天机器人”升级成“可路由、可升级、可审查”的客服闭环。

范围：

- 建立 `front_desk + planner + 5 个执行 Agent`
- 建立基础问题单状态机
- 加入 `quality_reviewer_agent`
- 前端展示当前处理状态、转人工状态、责任 Agent

交付标准：

- 所有会话都能进入显式状态流转
- 关键回复支持审查通过后再输出
- 高风险问题可稳定升级人工

### Phase 2：巡查与任务调度

目标：让系统具备“不会轻易卡死”的运营保障能力。

范围：

- 新增 `operations_patrol_agent`
- 引入 recurring 任务与定时巡检
- 支持阻塞标记、自动恢复、异常告警

交付标准：

- 卡住会话可被识别
- 失败任务可自动恢复或升级
- 后台可看到巡查轨迹

### Phase 3：绩效与知识运营

目标：让系统具备持续优化能力。

范围：

- 建立 Agent 绩效统计
- 新增知识缺口分析
- 建立 Flow/Skill 效果对比

交付标准：

- 可以量化看出哪个 Agent/Skill/Flow 更有效
- 可以追踪高频驳回和高频转人工原因

### Phase 4：可视化编排与流程版本化

目标：让运营人员能配置，不再依赖开发频繁改代码。

范围：

- Flow Builder
- AgentTemplate/Skill 可视化绑定
- 流程版本发布与回滚

交付标准：

- 运营可编辑问题处理流程
- 新版本可灰度、回滚、对比

## 16. 对你当前规划的明确建议

如果要把 OpenMOSS 思路引入你这个项目，最重要的不是“先做 cron 自唤醒”或“先做排行榜”，而是先完成这三个落点：

1. 把客服角色体系定清楚
2. 把会话状态机和审查返工闭环定清楚
3. 把 Agent 能力边界改成 Skill 驱动

一旦这三点落稳，后面的巡查、绩效、recurring、管理后台都会自然长出来。

反过来，如果这三点没定好，哪怕你先做了很多“多 Agent 协作”和“自动化运营”功能，系统也会因为岗位边界不清、任务状态不明、质量无法审计而很快失控。

## 17. 下一步建议

基于这份总计划，建议你下一轮直接继续补三份落地文档：

1. `虚拟人客服角色与岗位说明书`
   - 把每个 Agent 的职责、输入、输出、边界、升级规则写成标准定义
2. `虚拟人客服任务与状态机设计`
   - 把 ticket/task/review/patrol 的状态流转和字段补齐
3. `虚拟人客服 Phase 1 实施清单`
   - 直接映射到前后端改造项、表结构改造项、接口改造项

这样文档体系会变成：

- 总计划：为什么这样做
- 角色规格：谁负责什么
- 状态规格：系统怎么运转
- 实施清单：代码怎么改

这比单独讨论“要不要参考 OpenMOSS”更接近真正可执行的方案。
